# 远程接入、账号服务与 Relay 规划

状态：分期规划。本地 IPC、显式 TCP 与[手动证书 mTLS](../mtls.md) 已实现；
扫码配对、设备级授权撤销、账号服务和 Relay 尚未实现。本文规定后续产品边界与阶段验收；当前连接方式见
[服务连接类型](../connections.md)，业务接口见 [RPC 接口](../rpc.md)。

## 核心决策

Bas 采用“账号管理设备，客户端访问服务端执行环境”的模型，不实现服务端内部的多用户隔离。

- 一个 **Bas 服务实例**就是一个接入点，提供一份共享的 Agent 执行环境。
  接入点不等于物理机器；同一台机器可以独立部署多个实例。
- 服务端的系统运行身份决定 Agent 的权限。以普通用户运行就使用该用户的环境，以 root
  运行就使用 root 的环境；不根据远程登录账号切换 Linux / Windows 用户，也不额外禁止 root。
- 获准连接同一服务端的客户端默认共享会话、Agent 配置和模型登录状态。
  不承诺这些客户端之间的数据或执行隔离；既有工具审批策略仍然适用。
- 客户端可以连接多个服务端，一个服务端也可以接受多个客户端。
- 第二期引入账号后，每个服务端实例只归属一个账号。账号中心可以管理多个账号，
  但这不使单个 Bas 服务端变成多租户执行系统。
- 账号中心支持官方托管和自部署；不要求第一期部署账号中心。

这里的“远程登录”指凭借授权接入 Bas 服务，不是 SSH 式系统用户登录。
Bas 接入认证与 Agent / 模型提供方的登录是两件事，后者仍属于服务端执行环境。

## 三期路线

| 阶段 | 目标 | 授权管理 | 网络路径 |
| --- | --- | --- | --- |
| 第一期：远程登录 | 独立完成加密认证、多服务连接和会话重连 | 服务端本地管理客户端凭证 | 直接连接 |
| 第二期：账号服务 | 用账号统一管理服务端和客户端 | 账号中心管理设备归属和访问授权 | 继续直接连接 |
| 第三期：Relay | 在不能直连时仍可接入，作为远期目标 | 复用既有授权 | 直连优先，按需中继 |

第一期不为后两期预先实现账号数据库、OAuth 服务、设备发现云服务或 Relay。
后续阶段应扩展授权来源和网络路径，而不是重写 Agent 会话协议。

## 连接类型与本地免配对

客户端和服务端使用显式连接目标，不以单一 `SocketAddr` 表达所有传输：

| 类型 | 身份依据 | 默认行为 |
| --- | --- | --- |
| 本地 IPC | 操作系统用户身份；Unix socket / Windows Named Pipe | 默认启用，无需配对 |
| 明文 TCP | 无身份认证，回环地址也不代表某个用户 | 保留，用户显式配置才开启 |
| 远程 TLS | 当前为手动配置 CA 和客户端证书 | 显式配置；自动配对仍是规划 |

Windows 是本地 IPC 的实现平台，不使用 TCP 回退代替 Named Pipe。
本地 IPC 失败时明确报错，不自动连接无认证端口。
TCP 不只用于开发，用户可以按部署需要显式使用，不额外要求确认开关。
服务端可以同时启用多个入口，它们访问同一份执行环境。

本地免配对只适用于操作系统可以确认的同用户连接；它是接入授权，不是服务内部多用户隔离。
服务端的可信连接信息来自传输层，不接受客户端 RPC metadata 自报“本地用户”。
以后加入账号服务和扫码配对，不应让日常本机使用被迫走远程注册流程。

## 第一期：独立的远程登录

### 目标与范围

没有账号中心时，用户也能从 BasT / BasG 直接连接远程 Bas：

```text
客户端 ── 加密连接与双向认证 ── Bas 服务端
```

包含：

1. 远程服务地址配置、加密传输、服务端身份验证和客户端认证。
2. 服务端登记、查看和撤销客户端凭证；客户端完成首次授权后可以保存凭证并再次连接。
3. 客户端保存多个连接配置，选择目标服务，并分别维护连接状态和错误。
4. 远程使用已有业务 RPC，包括会话管理、Agent 管理、交互审批和事件订阅。
   远程访问不能只保护会话接口而遗漏其他管理接口。
5. 断线后重新认证并接入已有会话，沿用游标回放和提交语义，不自动重发可能已执行的任务。

连接配置包含服务地址、服务信任信息和客户端凭证引用；一期不需要填写账号中心用户。
配置里的显示名称不是服务身份，凭证引用也不是把私钥直接嵌入可分享的配置文件。

### 认证方向

优先采用成熟的 TLS 双向认证（mTLS），不自行设计 challenge / 签名登录协议：

- 服务端持有自己的身份密钥和证书，客户端验证目标服务身份。
- 客户端持有独立设备密钥和证书；服务端验证证书及该客户端当前是否获准访问。
  证书链验证成功不等于已经获得业务访问权。
- 首次接入通过可信配对信息或带外核对建立服务信任，并登记或签发客户端证书。
  未经验证的网络连接不能自行成为信任依据。
- 私钥留在设备本地。服务端管理客户端身份、公钥或证书及授权状态，
  不要求不同客户端共用一份私钥。
- 使用现有 TLS 库处理连接认证和加密。配对是建立初始信任的流程，不是另一套自制加密协议。

客户端断开或删除本地连接配置，与服务端撤销设备授权是不同操作。
凭证撤销必须阻止后续认证；已建立连接和长流的失效策略应在一期实现设计中明确并验证，
不能仅依赖下一次 TLS 握手。撤销访问本身不等于取消已在服务端运行的 Agent 任务。

### 扫码配对与连接配置

第一期采用“动态配对二维码 + 客户端本地生成密钥 + 自动保存连接配置”。
扫码不是导入一份包含长期凭证的静态配置，而是启动一次性设备授权；整个流程不依赖账号中心或 Relay。

#### 用户流程

1. 用户在服务端主动选择“添加客户端”，生成临时邀请，并在服务端界面或终端显示二维码。
2. 客户端扫码，取得配对入口、服务端公钥指纹和邀请凭据。
3. 客户端建立 TLS 连接并核对服务身份，展示服务名称和地址，请用户确认添加。
   身份验证失败时停止，不向对端提交邀请凭据。
4. 客户端在本机生成设备密钥，向服务端提交邀请凭据和证书签名请求（CSR）。
5. 服务端验证邀请及 CSR 的私钥持有证明，登记并授权客户端，签发客户端证书，
   返回完整连接配置。成功注册消耗该邀请。
6. 客户端保存证书、服务信任信息、地址及本地私钥引用，将服务加入连接列表；
   后续直接使用 mTLS 连接，不重复扫码。

用户不需要手动复制证书或配置 CA。服务端设备列表应显示新登记的客户端，并允许单独撤销。
正式业务地址等完整配置在可信连接建立后返回，不必全部放进二维码。

#### 二维码内容

| 字段 | 用途 |
| --- | --- |
| 格式版本 | 解析与后续升级兼容 |
| 配对入口地址 | 客户端初次连接的位置 |
| 服务端公钥指纹 | 将网络对端绑定到用户信任的服务端 |
| 一次性邀请凭据 | 授权本次设备注册 |
| 显示名称，可选 | 供确认界面展示，不作为服务身份 |

使用应用链接承载配对信息。以下仅为格式示意，不是已实现或已经冻结的协议：

```text
bas://pair?v=1&endpoint=...&pin=...&invite=...
```

扫码、粘贴配对链接、导入二维码图片复用同一个解析和配对流程；无摄像头的客户端也能添加服务。
协议版本、字段编码和长度限制在实现时明确，不将完整证书链或大块配置直接塞进二维码。

二维码不得包含服务端私钥、客户端私钥、永久访问令牌或模型提供方凭据。
客户端私钥在本机生成且不离开本机，不让多个客户端共享预先生成的私钥。
二维码和配对链接包含临时授权秘密，不作为普通诊断信息写入日志。

#### 首次信任与配对入口

二维码是带外信任来源，用户应从其信任的服务端界面或终端获取。
客户端核对 TLS 对端持有的公钥与二维码中指纹一致，而不是禁用 TLS 身份验证。
指纹基于证书中 SPKI 公钥计算，可采用 SHA-256；相同密钥更新证书不改变公钥指纹，
真正换钥仍需明确的信任更新流程。网络对端不能用自报指纹替代二维码中的信任信息。

首次配对时客户端尚无证书，因此配对入口与业务入口必须有不同的访问条件：

- **配对入口**：使用服务端 TLS 认证，以一次性邀请授权客户端注册，不要求已有客户端证书。
- **业务入口**：要求已授权客户端完成 mTLS 认证；未配对客户端不能访问会话或其他业务 RPC。

第一期优先考虑独立配对监听入口，仅在用户主动开启配对时提供注册能力。
是否复用端口在传输实现时确定，但不能为了配对而放开业务接口。
配对入口和返回的业务入口之间必须有可验证的服务身份关联，不能导入一个未受信任的新地址后跳过验证。

#### 邀请生命周期与可达性

- 邀请凭据使用密码学安全随机源生成足够长的随机值，不以几位数字作为唯一注册凭据。
- 默认建议 5 分钟有效，由服务端检查有效期；成功使用一次即失效，并支持取消和重新生成。
- 注册与邀请消费必须防止并发重复使用，同一邀请不能授权两个不同客户端。
  响应丢失后的重试或恢复流程不能绕过这一约束，具体语义在实现前细化。
- 默认持有有效邀请即可完成注册，不再要求服务端二次点击确认。
  若需在共享屏幕展示，可后续增加服务端人工批准模式，不作为一期默认流程。
- 二维码相当于临时邀请，拿到它的人可以尝试注册；不应作为公开、长期有效的服务名片。
  静态二维码可作为后续公开入口发现方式，但其本身不自动授予访问权。
- 扫码解决配置与信任，不解决网络可达性。服务端应允许配置对客户端公布的地址，
  不把 `0.0.0.0`、`::` 等监听地址直接当作连接地址，也不能假定内网地址对所有客户端可达。
  第一期仍要求客户端能直接访问配对入口和业务入口。

第二期可在扫码入口上增加账号绑定和账号授权；第三期可增加 Relay 网络路径。
这些扩展不要求仅因接入账号中心或更换路径就替换已建立的设备身份和凭证。

### 非目标

- 不创建 Bas 账号体系，不实现邮箱注册、密码登录或找回密码。
- 不实现系统用户切换、服务端多用户隔离、团队共享或细粒度角色权限。
- 不实现 OAuth/OIDC、自动云端设备发现、NAT 穿透或 Relay。
- 不把 SSH、Unix socket 或 Windows 用户登录作为远程协议的前提。
- 不通过本期规划扩大现有平台支持范围；平台可用性另行验证，连接模型不绑定 Linux。

### 验收场景

1. 一台客户端保存并连接两个服务端；会话、事件、凭证和错误状态不会串到另一服务。
2. 两台独立客户端获准访问同一服务端，并访问同一份会话和 Agent 环境。
3. 未登记、已撤销或无效的客户端凭证不能访问业务 RPC；
   服务身份不匹配时客户端拒绝连接，不静默接受替换的服务。
4. 撤销一个客户端不影响另一个客户端；已建立连接和长流遵循明确的撤销失效规则。
5. 断网后可以重新认证、按游标恢复订阅，不重复提交 prompt 或其他有副作用的操作。
6. 整个流程在没有账号中心的环境下可用。配置格式、CLI 命令、GUI 入口和迁移方式有对应说明。
7. 客户端通过二维码或等价配对链接完成首次授权、保存配置，随后无需再次扫码即可连接；
   扫码、粘贴链接和导入图片采用相同的配对语义。
8. 过期、已取消、已使用的邀请不能注册客户端；并发使用同一邀请最多授权一个客户端。
9. 服务端公钥指纹不匹配时，客户端不提交邀请凭据、不保存受信任配置；
   没有客户端证书的配对连接不能访问业务 RPC。
10. 二维码只携带配对所需信息，不包含长期私钥或模型凭据。
    地址不可达时明确报告连接问题，不把“二维码解析成功”视作“服务已连接”。

## 第二期：账号服务

### 目标与范围

用账号统一管理服务端和客户端，减少逐台配置连接与分发授权的工作：

```text
                    账号中心
                   /        \
          登录、设备列表      绑定、授权管理
                 /            \
              客户端 ────── Bas 服务端
                       直连
```

包含：

1. 官方托管与自部署账号中心使用一致的接入协议。
2. 用户登录后查看、命名、管理账号名下的服务端和客户端。
3. 服务端通过配对或浏览器确认绑定账号，适用于没有图形界面的服务器；
   不要求在服务端保存用户的账号密码。
4. 客户端登录后发现服务端并取得访问授权，无需逐台手工复制地址和长期凭证。
5. 支持解除服务端绑定、撤销客户端，并使授权变更作用于相应服务端。
6. 首版账号规则保持简单：同一账号名下、已获准登记的客户端可以访问该账号的服务端。
   暂不做团队、跨账号共享和角色体系。

账号身份包含账号中心身份，不同自部署中心中的同名账号不是同一个账号。
不要求首版支持账号中心之间的联邦互通。

### OAuth/OIDC 与设备凭证

- **OAuth 2.0** 表达访问授权，**OIDC** 提供账号登录和身份信息。
- 浏览器登录采用授权码流程与 PKCE；无浏览器的 CLI 或服务端可采用设备授权流程。
- 优先集成成熟身份服务，不从头实现 OAuth/OIDC 协议。Bas 账号服务重点处理设备归属和访问授权。
- 推荐先让账号中心管理第一期已有的设备授权：账号登录批准设备登记，
  设备连接继续使用既有凭证，避免为了账号登录重写连接层。
- OAuth access token 直接访问 Bas 是后续可选认证方式，不要求第二期同时支持两套连接认证。
  若采用，服务端必须验证签发者、目标服务、有效期和权限，不能把任意登录令牌当作授权，
  也不能用 OIDC ID token 替代 API access token。

账号中心不需要持有设备私钥。设备密钥证明设备身份，账号关系决定哪些设备可以访问哪些服务；
公私钥和 OAuth/OIDC 不是互斥方案。

### 运行边界与验收

- 账号中心负责账号、设备发现和授权，Agent 请求、事件及文件仍在客户端与服务端之间传输。
- 设备可被发现不代表网络可达；第二期不以 Relay 为前提。
- 账号中心短暂不可用不应直接终止服务端已有任务。新连接能否使用缓存授权、
  缓存有效期和撤销传播必须一起设计，不能同时承诺无限离线使用与撤销立即生效。
- 一期独立部署方式继续可用，接入账号中心不是所有服务端的强制升级条件。

验收至少覆盖：

1. 服务端绑定账号后，新客户端登录该账号即可发现、获准访问并直连服务端。
2. 官方托管与自部署账号中心使用同样的绑定、登记和撤销流程。
3. 账号或账号中心不同的设备不会因为名称相同而混用身份或获得授权。
4. 解除绑定和撤销按照定义传播；账号中心离线时的行为与文档约定一致。
5. 不接入账号中心的第一期客户端与服务端仍可完成独立认证和会话操作。

## 第三期：Relay（远期目标）

### 目标与范围

客户端与服务端不能直连时，通过中继建立连接：

```text
客户端 ───── 直连优先 ───── 服务端
   └──────── Relay ─────────┘
```

包含连通性探测、按需 NAT 穿透、直连失败后的中继，以及中继连接管理、访问控制和带宽限制。
不在前两期预先建设这套网络基础设施。

原则与验收：

1. Relay 只改变网络路径，不改变服务身份、访问授权和业务 RPC。
2. 客户端与服务端的加密认证跨过 Relay 保持端到端；Relay 不持有两端私钥，
   不以解密 Agent 内容作为转发前提。
3. 直连失败时可通过 Relay 完成同样的认证和会话操作，撤销策略同样有效。
4. 网络路径切换或中继重连沿用既有重连与游标语义，不承诺连接永不中断，也不自动重复提交任务。

## 跨阶段保持的边界

- **服务身份与地址分离**：换地址、换网络路径不创建新的服务身份。
  稳定服务标识仍需与受信任密钥绑定，不能只相信对端自报的标识；换钥有明确的信任更新流程。
- **授权与账号登录分离**：一期使用服务端本地授权，二期增加账号中心管理，
  业务接口不应依赖某个账号提供方的登录协议。
- **执行身份与远程身份分离**：无论由哪个客户端、账号中心或网络路径接入，
  都使用该服务端既定的执行环境，不隐式提权或切换系统用户。
- **连接与任务生命周期分离**：连接断开不等于任务取消；进程重启后的可恢复能力仍由既有存储及后端能力决定。
- **多服务状态分离**：客户端资源标识和本地缓存包含所属服务，操作始终指向明确的目标服务，
  不能仅凭会话 ID 或全局“当前连接”路由后台操作。

这些是实现边界，不要求第一期提前引入通用认证插件框架、账号服务或 Relay 抽象。

## 实现前待细化

三期顺序、共享执行环境、一期独立认证和扫码配对流程已确定；以下细节在对应阶段落地前细化：

- **一期**：配对链接编码、证书签发与校验细节、配对监听方式、邀请有效期配置及失败重试语义、
  凭证保存与轮换、既有连接撤销、本地连接兼容策略，以及 CLI / GUI 配置和操作入口。
- **二期**：身份服务集成、账号中心协议、设备绑定与解除绑定规则、
  授权缓存与撤销传播、既有独立服务的接入流程。
- **三期**：网络连通性方案、Relay 部署与资源限制、端到端加密的传输封装。
